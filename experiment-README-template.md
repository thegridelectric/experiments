> What this is: one line — the question asked or the incident
> investigated, and where the verdict lives (the logbook entry is the

## Why

The design question or trigger, stated so a reader who brings nothing
can see what hangs on the answer.

## Setup

What ran, where, and under what protocol (services stopped, windows,
safety nets). For a `-postmortem`: impact and contributing causes
sections instead, per the logbook genre note.

## Found

The findings, distilled. PASS/FAIL where the experiment had a bar.

## Timeline

Timestamped narrative of what happened (ET), one bullet per event.
For designed experiments this can be short; for postmortems it is the
backbone.

## Analysis notes

Reading keys, data-quality caveats, interpretive warnings — anything a
future analyst needs before trusting the numbers.

## Folder contents & experimental method

Open with HOW THE DATA WAS OBTAINED, before any file listing: for each
kind of data in the folder, say whether it came from the immutable
store (journal DB / S3 eventstore — re-pullable by anyone, the fleet's
own reporting) or was GENERATED by this experiment (measurements taken
by the experiment's own instruments/harness — in no store; a re-run
produces a NEW dataset, never a regeneration). If the experiment
touched the running system to take its measurements (stopped a
service, held a bus), say so here.

Then every committed file, one bullet each: what it is, where it came from,
how to regenerate it (or why it cannot be — external evidence gets a
provenance header in the file and an EXTERNAL EVIDENCE note here).
Committed data files are sema instances or external evidence only;
CSV views are generated on demand and gitignored.

This section MUST include, copy-pasteable on their own lines:

1. The command(s) that regenerate everything from scratch (the full
   pull / harness run / emit chain).
2. At least one explicit command generating a display CSV from an
   existing instance JSON in this folder — and when several views are
   likely wanted, one command line per view.

If the folder holds a `gw.readings` instance, end with the standard
paragraph:

---

**From the instance to the display CSV.** The `*-gw.readings-000.json`
file is the canonical record: the channel words together with their
readings, validating against the sema registry. The `-display.csv`
sibling is presentation only — the same readings as natural-unit floats
(temperatures °F, flows gpm), converted per each channel word's own
encoding. Regenerate it any time, with no database or S3 access:

    uv run python ../pull_readings.py --display-from <instance>.json
