# gwwf-obs-roundtrip, 2026-08-11

> What this is: the witness that gwwf's publish path delivers a
> decodable `gw.weather.observation` over a real broker with the
> location alias as the radio channel — the wire contract weather
> consumers will bind (OPS-436 build step 1).

## Why

The gw.weather vocabulary (staging) had never touched a broker. Two
things hang on this witness before any consumer code is written: the
routing-key shape consumers bind — specifically that the radio-channel
tail keeps its dots, so per-segment wildcard bindings work — and that
a broker-delivered body decodes through the vendored snapshot back to
the published instance.

## Setup

Local `gw-dev-rabbit` (the baked dev image: vhost `d1__1`, generated
topology). gridworks-weather-forecast at commit `f4f3d01` (gwbase
0.5.8, vendored staging snapshot). Publisher = a `GridworksActor` with
`TransportClass.WeatherForecastService` and the gwwf dev identity
(`d1.weather.dev`) — gwwf's real publish path minus the legacy NWS
poller. Consumer = a bare `ActorBase` tap whose ONLY binding is the
slug, via `subscribe_broadcast(radio_channel="us.me.millinocket")` on
`weathermic_tx`. Decode via the snapshot `SemaCodec` with
`expect=GwWeatherObservation`.

## Found

**PASS.** One publish, one delivery, on the expected key:

    rjb.d1-weather-dev.weather.gw-weather-observation.us.me.millinocket

- Alias and type name dash-rendered; the radio-channel tail keeps its
  dots (per the gwbase transport spec: the tail is one or more extra
  dotted segments) — per-segment wildcard bindings are therefore
  available to consumers.
- The slug-only binding delivered the message; the decoded instance
  equals the published one dict-for-dict.
- Bonus finding: `GridworksActor` boot validation rejected the
  synthesized all-zeros dev `GNodeId` (`uuid4.str` format enforced at
  the identity boundary). The dev `g_node.json` was regenerated with a
  real uuid4 — any other synthesized dev identity from the pre-0.5.x
  era will hit the same wall at first boot.

## Analysis notes

- Channel names here (`us.me.millinocket.temperature`, `.windspeed`)
  are the design's names as constants; the canonical `.gt` channel
  records land at OPS-436 build step 4, and the emission scheduler —
  not this harness — is what will read them. Re-check the names
  against the records when they exist.
- The witness pins the observation stream shape only; the forecast
  stream (radio channel = full forecast channel name, one message per
  forecast channel) is witnessed when the emission scheduler exists.

## Folder contents & experimental method

All output here was GENERATED by the harness run against the local
dev broker — nothing came from the journal DB or the S3 eventstore,
and no running fleet system was touched. A re-run produces a fresh
witness (the published values are constants; the ObservationTime is
the run hour), so nothing beyond code and this README is committed.

- `roundtrip.py` — the harness: publisher + slug-bound tap in one
  process; asserts decode equality and exits non-zero on any miss.
  Repointed post-run at `gwwf.names` for the channel/location
  constants (no semantic change; re-verified PASS) — re-running now
  needs gwwf at the NWS-adapters commit or later.

Regenerate everything (needs the local dev broker up):

    cd ~/GridWorks/gridworks-weather-forecast
    uv run python ../experiments/2026-08-11-gwwf-obs-roundtrip/roundtrip.py
