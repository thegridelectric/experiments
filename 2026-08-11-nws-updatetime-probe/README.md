# nws-updatetime-probe, 2026-08-11 (RUNNING)

> What this is: a day-or-two poll of the CAR/60,114 hourly product's
> time stamps, quantifying how fresh `updateTime` (the stamp gwwf
> binds to ForecastCreated) actually is at :30 past the hour — the
> planned forecast broadcast phase (OPS-436).

## Why

The gwwf emission design broadcasts forecasts at :30 and stamps each
revision with the product's `updateTime` — never `generatedAt`, which
refreshes per render even when the underlying data is hours older.
Two assumptions need numbers before the emission scheduler's contract
is trusted: how old `updateTime` typically is at :30, and how often
consecutive :30 polls carry the same revision (which the design
treats as "same revision, still alive" idempotent re-emits).

## Setup

`probe.py` polls the hourly product every 5 minutes from the dev
machine and appends one JSONL line per poll (`polled_at`,
`update_time`, `generated_at`, `first_period_start`, HTTP status or
error). Started 2026-08-11 ~12:05 ET (pid in `probe.pid`); stop by
killing that pid after a day or two, then analyze.

## Found

Open — analysis after the run. First poll (12:05 ET) already shows
the gap the design anticipated: `updateTime` 09:09Z against
`generatedAt` 16:00Z — the underlying data was ~7 h old while the
render stamp looked fresh.

## Analysis notes

- `update_time` / `generated_at` are recorded verbatim (offset form);
  normalize when analyzing.
- A `status` other than 200 or an `error` line is a poll miss, not a
  product gap; the product's own availability is what matters.
- **Gaps in `polled_at` mean the probe was suspended, not that NWS
  changed.** macOS App Nap suspends a plain nohup'd background python
  between polls (two early launches went silent within minutes while
  still "alive", state SN); since 13:39 ET the probe runs under
  `caffeinate -i`, which exempts it. A lid-closed machine still gaps.
- Early findings (interim, small sample): the 09:09:03Z revision held
  through at least 12:05–12:33 ET — lag 417→444 min, spanning a :30 —
  while `generatedAt` refreshed per poll; the next revision
  (16:33:26Z) appeared by 13:39 ET. The ForecastCreated←updateTime
  binding is already vindicated; :30 freshness looks unreliable.

## Folder contents & experimental method

All data here is GENERATED by this probe polling the live NWS API
from the dev machine — nothing from the journal DB or S3, no fleet
system touched. A re-run produces a new dataset.

- `probe.py` — the poller (5-min cadence, `--once` for a smoke test).
- `probe.jsonl` — accumulating raw polls (uncommitted while running;
  committed with the analysis).
- `probe.err` / `probe.pid` — run mechanics, gitignored-grade;
  not committed.

Regenerate / restart (`caffeinate -i` defeats App Nap — see Analysis
notes):

    cd ~/GridWorks/gridworks-weather-forecast
    nohup caffeinate -i uv run python \
      ../experiments/2026-08-11-nws-updatetime-probe/probe.py \
      >> ../experiments/2026-08-11-nws-updatetime-probe/probe.jsonl 2>> \
      ../experiments/2026-08-11-nws-updatetime-probe/probe.err &
